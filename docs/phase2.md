# Swarm Coder: Architecture Improvement Plan for Robustness and Scalability

This document outlines a comprehensive plan to enhance the `swarm_coder` framework, focusing on making it capable of handling large-scale codebases reliably.

## 1. Current Problems

Based on an analysis of the existing `swarm_coder` architecture, the following critical bottlenecks and vulnerabilities have been identified:

### 1.1 Inefficient File Modification (The "Full File Rewrite" Problem)
*   **Description:** The `CoderAgent` relies on rewriting the entire contents of a file to make changes (seen in `phases.py` and the prompt instructions).
*   **Impact:** This is extremely token-inefficient and highly prone to hallucination or accidental deletion of existing code when dealing with files larger than a few hundred lines. The parsing logic in `run_execution_phase` (looking for markdown code blocks) is also brittle.

### 1.2 Lack of Automated Validation (No Self-Healing)
*   **Description:** Code generated by the Ollama model is written directly to disk. There is no automated step to verify if the code is syntactically valid or if it resolves the assigned task.
*   **Impact:** A single syntax error generated by a coder will halt or break the resulting application. The system lacks the ability to self-correct based on compiler or linter feedback.

### 1.3 Context Overload in Review/Planning Phases
*   **Description:** The `run_reviewer_phase` (currently commented out) attempts to load the content of *all* valid files in the workspace into the LLM's context. The Planner also lacks targeted search tools.
*   **Impact:** For larger codebases, this approach will rapidly exceed context window limits, leading to expensive API calls and degraded reasoning capabilities due to "lost in the middle" phenomena.

### 1.4 Manual Tool Execution Bypassing the Framework
*   **Description:** While tools like `write_file_content` are registered with the `CoderAgent`, the execution loop in `phases.py` manually extracts code blocks from a stream and writes them to disk, bypassing the native tool-calling capabilities of the agent framework.
*   **Impact:** This reduces the agent's autonomy and makes it difficult to introduce more complex tool interactions in the future (e.g., read, then edit, then verify).

## 2. Proposed Solutions and Implementation Strategy

### 2.1 Solution: Targeted File Editing Tools (Replaces Full File Rewrite)
Instead of rewriting files, the system must support targeted edits.
*   **Implementation Steps:**
    1.  Create an `edit_file` tool.
    2.  Update Coder Prompt to use it.
    3.  Refactor Execution Phase to use ADK runners natively.

### 2.2 Solution: Automated Validation Loop (Self-Healing)
*   **Implementation Steps:**
    1.  Create a `run_command` tool.
    2.  Add a validation step in the Execution loop.
    3.  Feed errors back to the CoderAgent for retries.

### 2.3 Solution: Context-Aware Review Phase
*   **Implementation Steps:**
    1.  Re-enable `run_reviewer_phase`.
    2.  Targeted context (only modified files).
    3.  Integrate `git diff`.

### 2.4 Solution: Advanced Discovery Tools for the Planner
*   **Implementation Steps:**
    1.  Add `grep_search`.
    2.  Add directory exploration.
    3.  Update Planner Prompt.
